# Flashcard Application

A small full-stack flashcard application built with PHP, React, TypeScript, and MySQL.

The goal was to keep the solution simple, clear, and easy to extend while meeting the requirements of the assessment.

## Setup Instructions

### Backend

From the repository root:

```bash
docker compose up --build
```

API:

```text
http://localhost:18080
```

MySQL:

```text
localhost:33066
```

### Frontend

From the `frontend` directory:

```bash
npm install
npm run dev
```

Open:

```text
http://localhost:5173
```

If the API runs at a different address, set `VITE_API_URL`.

## Architectural Decisions

### Backend

The backend uses a **lightweight Clean Architecture** to keep Domain, Application, HTTP, and persistence responsibilities separated without adding unnecessary complexity.

Slim 4 was chosen instead of plain PHP or a heavier framework such as Laravel. It provides routing, middleware, request/response handling, and error handling while keeping the architecture explicit.

Validation is performed before the Domain, while the Domain also protects its own rules so invalid flashcards cannot be created from other entry points such as CLI commands, queues, or tests.

Flashcards use **UUID v4** identifiers generated by the application. This avoids relying on the database for ID generation. For a larger system, alternatives such as `BIGINT AUTO_INCREMENT` or UUID v7 could be considered.

The backend applies common OOP and SOLID principles, including:

- encapsulation
- abstraction
- composition over inheritance
- polymorphism
- Dependency Inversion Principle

Common patterns used include:

- Repository
- Dependency Injection
- Adapter

Dependencies are wired manually because the dependency graph is small.

### Frontend

The frontend is a React and TypeScript SPA built with Vite and React Router.

Code is organised by feature, with shared API, query, and UI code kept separately.

TanStack Query manages server state, caching, loading, errors, and data refresh after mutations.

Tailwind CSS is used for styling and Sonner for user feedback.

## Data Storage

MySQL 8 is used for persistent storage and runs through Docker.

SQLite would also have been sufficient for this task, but MySQL better represents an external database service.

## Trade-offs

- **Light Clean Architecture:** more structure than a simple layered solution, but clearer boundaries and easier testing.
- **Slim:** less framework overhead than Laravel, while avoiding plain PHP HTTP boilerplate.
- **Manual dependency wiring:** simple for this project; a DI container would make more sense as the application grows.
- **MySQL:** more setup than SQLite, but closer to a typical production database.
- **UUID v4:** simple and database-independent, but less index-friendly at large scale than sequential IDs or UUID v7.
- **TanStack Query:** adds a dependency, but reduces repeated server-state logic.
- **Feature-based frontend structure:** adds some nesting, but keeps related code together.

## Validation and Error Handling

The API validates user input and returns appropriate HTTP errors:

- `400 Bad Request` for invalid identifiers or malformed requests
- `404 Not Found` when a flashcard does not exist
- `422 Unprocessable Entity` for invalid flashcard data

## Testing

The backend includes:

- unit tests for Domain and Application behaviour
- one integration test for the real MySQL persistence layer

Most use-case tests use an in-memory repository so they remain fast and independent from MySQL.
